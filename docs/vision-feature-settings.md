# Model Registry, Vision and Feature Settings

All SiteFlow endpoints below use the existing authenticated `/api/v1` API and
CSRF protection for mutations and integration tests, including read-only probes.
Browser-direct provider probes are separate outbound requests, not SiteFlow API calls.

## Model Registry

Settings now uses the full-width **大模型** `ModelSettingsCard` in
`SettingsView`, not the old half-width/static `VisionSettingsCard`. The ordered
list accepts **0-20 database entries (including any legacy DB entry), plus one
optional environment entry, at most 21 total**. An environment entry does not
consume a DB slot: when it appears alongside 20 DB entries, all 21 remain visible
without truncating/dropping rows or disabling list operations. Adding a DB entry
is limited by the DB count, not the total row count. There is no required entry or primary/secondary UI
role. The internal ID `primary` only preserves legacy storage/API compatibility;
it does not confer priority or make an entry mandatory.

Each row shows priority, display/upstream model names, an enable switch, usage
tags, vision/text capability and configuration status. **上移 / 下移**, enabling,
disabling and removing a database entry edit a local draft only; explicitly click
**保存排序与启用状态** to persist them. Disabling is a temporary routing exclusion,
not deletion of the saved connection. **配置 / 添加模型** opens a modal for display
name, Base URL, upstream model name, API Key, `supports_vision`, `max_tokens`,
enabled state and usages. **保存模型与列表** saves the modal together with all pending
list order, enable and removal changes. Opening, refreshing or saving does not
contact a provider. The optional environment entry has the source label **环境变量**
in the UI (`source="env"` in the API): its entire
connection is read-only, its configuration modal cannot be opened, and it cannot
be deleted. Order and enable state remain saveable in the UI. Name/usage metadata
can be updated only through the API, not through the UI's unavailable modal.
The concise save hint is **保存前请测试连通性，测试不代表保存配置**. Keep technical
boundaries such as unimplemented MCP support in documentation, not long modal warnings.

| Usage | Runtime Consumer |
| --- | --- |
| `feature_cards` | Workflow model features and host-private assistant feature execution, with capability requirements per feature. |
| `assistant` | Persistent assistant turns, titles, summaries and failure takeover; also the retained text-only `/config-ai/generate` API. |
| `mcp` | Reserved metadata only. No MCP runtime/server, external identity or authorization grants are implemented. |

Usages are routing eligibility, **not tool permissions**. Target, execution,
screenshot, credentials, workflow and consumption-review authorization remain
independent. See [assistant boundaries](ai-assistant.md) and the
[unimplemented external Agent/MCP design](assistant-agent-mcp-authorization.md).

### Registry API

Paths here are relative to `/api/v1`:

```text
GET  /integrations/models
PUT  /integrations/models
POST /integrations/models/{model_id}/test
```

GET and PUT return `{revision, items}` in priority order. Each item contains
`id`, `name`, `enabled`, `usages`, row-level `source: "env" | "db"`,
`config_editable: boolean`, and `config: VisionView` (the field views described
under [Vision Integration](#vision-integration)). `available` means locally
configured/valid, not healthy or successfully tested, and does not imply enabled
or eligible for a usage. API keys are write-only; responses contain only
configured/source/editable/masked metadata, never the key or retired-key archive.
An ENV row has `source="env", config_editable=false`, even if some effective
fields are inherited from DB or unset. Row source and field sources are distinct.

PUT submits **the entire ordered metadata list**, not a sparse list patch:

```json
{
  "expected_revision": 0,
  "items": [
    {
      "id": "af5bff5f-781a-4a47-aad4-d61686130236",
      "name": "Workflow model",
      "enabled": true,
      "usages": ["feature_cards", "assistant"],
      "config": {
        "base_url": "https://model.example/v1",
        "model": "provider-model-name",
        "api_key": "REPLACE_WITH_YOUR_KEY",
        "supports_vision": true,
        "max_tokens": null
      }
    }
  ]
}
```

IDs must be unique; no `primary` entry is required and `items: []` is valid when
there is no environment entry. New IDs are canonical lowercase UUID4 strings
generated by the client. The legacy internal ID `primary` remains accepted for
compatibility, not as a UI role. Names are trimmed, nonblank and
at most 128 characters. `enabled` is a strict Boolean; usages are a unique subset
of the three values above (an empty list is allowed). Omitting an existing
database item removes it from active configuration, including the legacy entry.
Omitting an environment entry returns 409 `model_config_locked`.

`config` is optional and patches connection fields for that ID. Omitted fields
retain saved values. New entries need Base URL, model and API Key;
existing partial legacy DB configuration remains readable/editable so it can be
repaired rather than requiring a complete connection just to manage metadata.
An incomplete ENV entry is still read-only and must be repaired in deployment
settings, not completed in the UI.
Base URL is an HTTP(S) OpenAI-compatible `/v1` root, optionally under a path prefix,
without credentials, query or fragment (at most 2048 characters); upstream model
name is at most 256 and API Key at most 4096 characters. Blank values and null for
these string fields are rejected. The **modal** leaves an existing API Key blank
to keep it by omitting `api_key` from PUT; API clients must also omit it, not send
an empty string. New keys must be supplied explicitly.

Registry `max_tokens` accepts a strict JSON integer **0-2147483647** or null.
Positive values are sent unchanged to that entry's provider; null or 0 clears the
DB cap (stored as 0). Omission preserves it. Clearing the modal input sends null;
blank strings, booleans, fractions, negatives and numeric strings are not valid
registry API values. An unset/zero cap omits the upstream parameter and uses
provider defaults, not guaranteed unlimited output. There is no per-entry timeout:
all backend entries use `SITEFLOW_MODEL_TIMEOUT` (default 30 seconds,
maximum 300). Browser-direct probes instead have a fixed 30-second total budget.
Assistant settings may independently override the selected entry's Token cap;
null there means inherit, not clear. Existing response-byte limits remain in force.

The five `SITEFLOW_MODEL_*` connection settings listed below supply one optional
ENV entry. Any one present, including explicit false/0, locks **all five connection
fields**, not just fields with an environment value. Any connection patch returns
409 `model_config_locked`; metadata/order remain saveable. Effective legacy values
still merge per field with retained DB values, so omitting a cap or vision flag can
retain the DB setting without making that field editable. Other entries are DB-only
and inherit none of these overrides. Removing all five environment connection
settings restores DB editing. The global timeout alone creates/locks no entry.
No new SQL tables or columns are required. Deployment variables must be renamed:
**old `SITEFLOW_VISION_*` names are ignored, with no alias fallback**.

Saves use `expected_revision` plus an atomic encrypted-record CAS. A stale save
returns 409 `model_registry_conflict`; the UI preserves list/modal drafts and
**does not retry automatically**. Review before refreshing; confirmed refresh
discards unsaved edits, then re-edit against the new revision. A lost response is
not proof the save failed: refresh to establish the saved state before writing
again. Legacy connection PUT/DELETE also advance the registry revision, invalidating
old drafts, including revision 0.

Registry errors use static `detail.code` without input/provider secrets:
`invalid_model_registry` / `model_config_incomplete` (422),
`model_registry_limit` (422), `model_not_found` (404), and
`model_registry_unavailable` (503), in addition to the 409 cases. Malformed or
undecryptable registry documents fail closed, not as an empty/default registry.
Recognizable legacy field errors can instead be displayed with `available=false`
and field `error` metadata (notably URL/Token-cap errors) for repair; this is not
permission to use invalid connection data. An unreadable legacy secret can still
make the management read unavailable. PUT is limited to 256 KiB with a 10-second
body-read deadline (413 `request_limit`, 408 `request_timeout`); unknown fields,
duplicate JSON keys and non-finite numbers are rejected. Registry routes use
existing session authentication without touching its activity timestamp, require
CSRF for PUT/tests, and return `Cache-Control: no-store`. Legacy routes retain
their existing cookie/session-touch behavior.

### Saved and Current Configuration Tests

The row's **测试** keeps its existing saved-only behavior: it calls
`POST /integrations/models/{model_id}/test` **without a body**, testing only that
ID's saved effective connection, including any environment overrides. Pending
list/modal edits are not tested; the UI warns about them. A configured entry can
be tested even if disabled or without a runtime usage. No usage-based reselection
occurs, and the existing no-body API contract is unchanged.

The modal's **测试当前配置** previews the current connection **without saving**,
including for new or unconfigured entries. It is available independently of saved
configuration status, name, enabled state and usages, with connection validation
independent of save validation. Base URL must be an HTTP(S) `/v1` root, at most
2048 characters, without user information, query, fragment or control characters;
model is nonblank and at most 256 characters, API Key at most 4096, both without
control characters. The Token cap is blank/null or an integer 0-2147483647; blank/0
omits the upstream parameter. A key is required if the entry has no saved key.
An ENV entry has no editable modal; all its connection fields retain their effective
values and cannot be overridden by backend draft-test patches either.

| Current-Configuration Case | Request Path |
| --- | --- |
| New entry or nonblank typed API Key | Native browser `fetch` POST to the current Base URL plus `/chat/completions`, using the typed key and current connection parameters. No SiteFlow backend receives this key for testing. |
| Existing entry with no typed key | Authenticated, CSRF-protected POST to `/integrations/models/{model_id}/test` with `{expected_revision, config}`. The API merges a non-key draft patch with that exact saved entry's effective connection/key in memory only. |

The optional backend test body has this shape (the revision is the last read
registry revision, not a request to save):

```json
{
  "expected_revision": 7,
  "config": {
    "base_url": "https://model.example/v1",
    "model": "provider-model-name",
    "supports_vision": true,
    "max_tokens": null
  }
}
```

`config` is a sparse patch allowing **only** `base_url`, `model`, `supports_vision`
and `max_tokens`; omitted fields retain saved effective values. It never accepts
`api_key`, metadata, order or usages. Field types/limits match registry connection
validation. The ID must already exist; this is not a backend new-entry probe or a
way to obtain stored keys. A stale `expected_revision` returns 409
`model_registry_conflict`; patching any connection field of an ENV entry returns 409
`model_config_locked`. Drafts are retained, with no automatic save or retry.
If the endpoint changes while reusing a saved key, the modal requires an extra
explicit confirmation showing the target: this intentionally authorizes sending
that saved key to the edited URL. The stored key is never returned to the browser.

A typed key always stays on the browser path for testing, with **no automatic
backend fallback**, including after failure. It reaches SiteFlow's backend only
through a later explicit normal **保存** action. Browser POST uses
`credentials: "omit"`, `redirect: "error"`, `referrerPolicy: "no-referrer"` and
`cache: "no-store"`; its fixed **30-second** deadline includes reading the body,
with a **64 KiB** response-read cap. CORS, HTTPS-page/HTTP-provider mixed content,
network/TLS and blocked redirects are often indistinguishable to browser code;
diagnostics must not claim a specific cause without evidence or silently proxy the
request. Configure the final API root directly.

Backend probes use the global `SITEFLOW_MODEL_TIMEOUT` (default **30 seconds**,
maximum **300**), including a total deadline across request and body reading. They
do not follow redirects, reject encoded responses rather than decode unbounded
content, and enforce the **64 KiB raw-response byte limit** and bounded reads.
They require explicit CSRF validation even though the probe does not write state.
Both paths return only a result preview: no configuration writes, revision bump,
order/enable/usage changes or retired-key archive changes.

Diagnostics are safe Chinese messages, with HTTP status when available and timeout
phase only when known. They distinguish invalid JSON/response structure, refusal,
truncated output and empty/reasoning-only content. Only recognized provider error
codes/types and their **fixed safe explanations** may be displayed, never arbitrary
provider prose, completion text, raw response bodies, headers or secrets.
With `supports_vision=true`, the probe sends a valid tiny PNG and requires nonempty
final text; otherwise it sends text only. Browser success checks connectivity
**from the user's browser**, not from the API or Worker production environment;
backend success checks **from the API, not Worker**. Neither guarantees production
reachability, tool calling, real vision/recognition accuracy, authorization for
other operations or business success. Model usage selection is unchanged.

### Selection and Storage

Selection walks the saved list and chooses the **first enabled, configured entry
with the requested usage and, when required, vision capability**. It skips disabled,
wrong-usage and valid-but-incomplete entries; a disabled or wrong-usage legacy entry
does not block other eligible entries because of its connection validation.
An enabled, matching-usage legacy entry with invalid connection data still fails closed
when reached; skipping ineligible entries is not a corruption-recovery fallback.
Management reads can expose repairable field errors without requiring runtime
selection to succeed, so DB connection repairs and metadata edits remain possible.
An image request skips text-only entries; a text request need not prefer vision.
Selection does no provider health probe. Once selected, HTTP/network/timeouts,
refusals or invalid answers **never automatically try the next model** or another
input mode/OCR method. This is priority routing, not provider-failure fallback.
Thinking models may consume the Token budget on reasoning; leave enough for final
answers/tool calls. Reasoning is not an answer, and provider-specific reasoning
or Token parameters are not negotiated.

The existing encrypted `integration_configs` row **`models.registry`** stores the
version/revision, ordered metadata, new entries' connection fields/secrets and a
private `redaction_keys` archive. Legacy connections remain in the original five
`vision.*` rows with their existing AAD; these keys and the internal ID `primary`
are compatibility details, not user-facing roles. Merely reading or saving metadata
does not migrate/re-encrypt existing ciphertext. With no registry, reads synthesize
revision 0 and no entries unless legacy DB connection rows or environment connection
settings exist. In that case, one ordinary enabled entry is exposed with
`feature_cards` and `assistant` usages and MCP off. If an existing registry lacks
the environment entry, it is appended, not forced to the first position. Reads do
not write migration rows, change cookies or probe a provider.

Deleting the legacy DB entry through registry PUT also clears the active five
`vision.*` rows, so later reads do not resurrect it. Retired keys remain in the
archive only for redaction, never as a source of active connections or entries.

Rotation/removal/legacy clearing removes old keys from **active connections**,
not necessarily from encrypted storage: retired literal keys are retained solely
to redact historical logs. The deduplicated archive has at most **512 keys** and
is also subject to the 256-KiB encrypted document's plaintext-size budget; an
overflow rejects the whole mutation atomically rather than dropping old keys.
Archived keys are never used in provider runtime selection or returned by the API.
Do not promise permanent key erasure on delete/clear. Artifact-log redaction uses
all known model keys, including legacy, disabled, unused, reserved and retired
ones, before pagination; it does not expose those secrets to assistant history.
Provider credentials and the private runtime map are not workflow configuration,
plaintext history or model-visible tool output. Filtering remains bounded known-key
redaction, not general DLP. Back up the database and protect `SITEFLOW_MASTER_KEY`
separately.

Stop active work before upgrading **API, Worker and Web together**, and rename
deployment model variables. This document describes current code contracts, not
a production deployment or live-site test.

## Vision Integration

These are **legacy-entry compatibility interfaces**, not the registry selector:
`GET /integrations`'s `vision`, `PUT/DELETE /integrations/vision`,
`POST /integrations/vision/test`, and `IntegrationService.vision_runtime()` always
refer to the internal legacy connection (`primary`), even when it is disabled,
reordered, has no matching usage or another entry is selected for actual work.
They do not imply a primary model role or automatically select the first row.

`GET /integrations` includes `vision` with `base_url: ValueView`, `model: ValueView`,
`api_key: TokenView`, `supports_vision: BooleanView`, `max_tokens: NumericView`, and
`available: boolean`. `NumericView` contains `value: integer | null`, `source`,
`editable`, and optional `error`; null means unset and 0 means no explicit cap.
Available means configured and locally valid, not a successful provider probe. API
keys are never returned in plaintext.

`PUT /integrations/vision` accepts `{base_url?, model?, api_key?, supports_vision?, max_tokens?}`.
Omitted fields are unchanged. For `max_tokens`, a positive JSON integer sets the cap;
explicit null, blank/whitespace-only strings, or 0 clear the DB cap (stored as 0).
Negative values, booleans, fractions, and nonblank strings are rejected (422).
For the other fields, null is unchanged and empty strings are rejected. The base URL is an
HTTP(S) OpenAI-compatible `/v1` root, optionally under a path prefix, without URL
credentials, query, or fragment. Values are encrypted using the existing integration
key storage. `DELETE /integrations/vision` clears only the legacy connection's five
DB fields: Base URL, model, API Key, supports_vision and max_tokens. Existing
registry metadata and other entries remain unchanged. This compatibility clear is
not the same as removing the legacy DB entry through registry PUT, which removes
its metadata and active connection together. Neither promises retired-key erasure.
Any environment connection setting prevents all connection edits/clearing and
entry deletion (409); even DB-derived fields of the ENV entry are locked.

The optional environment connection uses:
`SITEFLOW_MODEL_BASE_URL` (OpenAI-compatible `/v1` root), `SITEFLOW_MODEL_API_KEY`,
`SITEFLOW_MODEL_ID` (upstream model name), `SITEFLOW_MODEL_SUPPORTS_VISION` and
`SITEFLOW_MODEL_MAX_TOKENS`. Blank URL/key/model values are unset. Set the vision
flag only when an ENV entry is desired: even false creates the read-only entry.
If omitted, it uses the retained DB flag or defaults to true; without any ENV
connection settings the DB flag is editable.

`SITEFLOW_MODEL_MAX_TOKENS` is an optional nonnegative integer output-token limit:
4096 sends `max_tokens=4096`; 0 omits that parameter and uses provider defaults,
**not unlimited output**. Leave the line commented out to keep a saved DB cap;
an empty value normalizes to 0 and still creates/locks the ENV entry. Effective
values merge with DB per field, but any one environment setting locks the whole
connection. To clear the DB cap in the UI, remove all five ENV connection settings,
then save blank/0. Existing DB values are retained under environment overrides.
`SITEFLOW_MODEL_TIMEOUT=30` controls request timeout in seconds for **all models**
(maximum 300), not entry configuration; it alone creates/locks no ENV entry.
Old-prefix variables are ignored: rename them in deployment, with no alias fallback.

The legacy PUT's blank/null/0 cap-clearing behavior is preserved; unlike registry
PUT, it accepts a blank string for this field. The legacy entry's cap is not a global
cap for every model: each routed request uses its selected entry's cap (plus the
persistent assistant's optional override). `supports_vision` still defaults to
true when no saved/environment flag exists. A text-only legacy entry does not
disable visual work if a later eligible `feature_cards` vision model exists. With no eligible vision
entry, image-character steps fail and quiz/grid steps require human handling;
`ddddocr` and `nexusphp_gd5` are unaffected. Legacy `/vision/test` still tests only
the saved legacy connection, using the same image/text probe described above.

The image-captcha features expose `captcha_method` as a normal step config field
whose default is `ddddocr`. It is also a global step default in Features management,
so each step can override the method. The available values come from the built-in
method registry; adding another method there automatically adds it to the schema,
step dropdowns, and Features management without changing the feature card. Current
methods:

- `ddddocr`: universal OCR, simple but less accurate. Only this method uses
  `min_confidence`.
- `vision`: first eligible `feature_cards` visual model. The step fails clearly
  when no such model is configured. It never silently falls back after a request failure.
- `nexusphp_gd5`: exact template matching for NexusPHP GD font-5 captchas. It supports
  standard 150×40 images containing six characters, automatically rescales differently sized images, and reports `match_margin`.

The image-captcha features also expose management-only `execution_settings` containing
`llm_prompt` (default asks for captcha characters only, preserving case). The prompt
is used only when the selected method is `vision`. `sign.image_quiz` exposes the same
`llm_prompt` field as a custom quiz instruction with an image-quiz-specific default
and always uses vision. `challenge.grid_captcha` has its own grid-specific default
prompt and always uses vision as well. Prompts are not step config fields or defaults. Runtime
integration secrets are sent separately from resolved workflow configs and are not
included in persisted workflow snapshots or recognition logs.

Worker requests include `feature_execution_settings: {"<feature key>":
{"llm_prompt": string}}` (or result-judgement behavior), containing only enabled,
supported features present in that execution. Connections are selected separately
per feature into the host-private `feature_model_runtimes` map, keyed by feature
key, not step key or registry ID. Image-character steps selecting `vision`, quiz
and grid require vision; an opted-in `flow.result` requires it only in screenshot
mode. Thus one workflow can use the first text model for result judgement and a
later vision model for a subsequent CAPTCHA, rather than one shared runtime for
the whole job. `ddddocr`/`nexusphp_gd5` and disabled steps do not request an LLM.

The map is frozen for the job and passed privately to Worker, separately from
workflow snapshots; neither it nor behavior prompts add provider secrets to
saved workflows. A present map is authoritative: missing/null feature entries
mean unavailable, never fallback to the old shared `vision` field. Worker accepts
that field only for old payloads with no map at all. Malformed maps fail closed.
Host-private isolated assistant model features likewise select `feature_cards`,
independently of the assistant's conversational model; isolated `flow.result`
remains Boolean-only under its existing contract.

`sign.image_quiz` always requires vision and has no ddddocr fallback. Without an
eligible configured visual model it returns `waiting_human`. It sends the cropped quiz image,
question text, and numbered visible options. The model must return a JSON object
with `is_clear`, `selected_index`, `need_refresh`, and optional `reason`; reasoning
content remains ignored. Unclear answers refresh the question up to `max_refresh`
times, then return `waiting_human`. Quiz requests use the selected entry's `max_tokens` setting.

### Grid Captcha

`challenge.grid_captcha` is a repeatable `challenge` feature with
`requires=["vision"]`. It is not an image-character captcha method: the
`captcha_methods` registry remains `ddddocr`, `vision`, `nexusphp_gd5`, and grid
steps have no `captcha_method`, input field, charset, or OCR fallback.

| Config Field | Code Default | Meaning |
| --- | --- | --- |
| `image_selector` | `[".geetest_panel_box", ".geetest_widget"]` | Ordered selector candidates for a capture region containing both the target reference and the entire 3x3 grid. The first matching region must include both. |
| `cell_selector` | `[".geetest_item"]` | Ordered candidates for grid cells, indexed 1-9 from left to right, top to bottom. |
| `selected_selector` | `.geetest_selected, .selected, [aria-checked="true"], [aria-selected="true"]` | CSS `matches` predicate against each cell itself, not a descendant lookup. |
| `refresh_selector` | `[".geetest_refresh"]` | Ordered refresh-button candidates. |
| `submit_selector` | `[".geetest_commit"]` | Ordered submit-button candidates. |
| `max_refresh` | `3` | Shared extra retry budget for unclear recognition, rejected answers with a regenerated grid, and stale challenges. Integer 0-10; default allows at most four rounds in total. |
| `success_signals` | `["验证成功", "驗證成功", "今天已经签到过啦", "今天已經簽到過啦"]` | Success text candidates; any match confirms success. Customize for the actual site. |
| `success_selector` | `[]` | Explicit success elements that appear. |
| `success_when_missing` | `[]` | All configured elements must disappear to satisfy this condition. No implicit panel-disappearance condition. |
| `success_wait_seconds` | `10` | Success-condition deadline, integer 1-120 seconds. |

Selector and text lists reject blank entries; the capture and cell lists must be
nonempty. The three success-condition types are alternatives; within
`success_when_missing`, all configured selectors must be absent/hidden. Do not use
only unused fallback panel locators: already-absent elements cannot prove a solve.
The schema permits all three success lists to be empty, but the
runtime contract is explicit `unknown` in that case, never unconditional success.
Panel disappearance alone is not a success signal unless explicitly configured.

`GRID_CAPTCHA_DEFAULT_PROMPT` instructs the model to compare the reference target
with the full 3x3 grid, use row-major indices 1-9, and select every matching cell,
including multiple matches. It forbids guessing and requests refresh when unclear.
The requested JSON fields are `is_clear`, `selected_indices`, `need_refresh`, and
optional `reason`. The management-only prompt is editable as
`execution_settings.llm_prompt`; it is neither a step override nor a provider
credential. Features management displays a dedicated grid prompt label and warns
that an eligible visual model is required. Reset restores this grid prompt, not the
character-recognition or image-quiz prompt.

Requests offer the `submit_geetest_result` function tool with `tool_choice="auto"`,
so thinking-model providers that reject named/required tool choices can use their
native tool parser without disabling reasoning. The selected model must support
image input and tool calling. A provider returning plain content is accepted only when
the entire content is valid JSON with the same fields; prose, invalid indices,
duplicate indices, and truncated answers are rejected. Raw provider error bodies and
reasoning are never logged; only the sanitized error fields described below may
appear in admin diagnostics. Only the captured widget PNG is sent, not page text,
cookies, or an arbitrary image URL fetched by the Worker.

The Worker pins the challenge DOM and image sources before recognition. It
rejects preselected cells and changed/replaced challenges, verifies the exact
selected set before submission, and dispatches DOM clicks as in the reference
script. Before recognition the grid must remain unchanged across two guarded
reads. Unclear recognition, wrong selections that produce a new empty grid, and
stale challenges all consume the same `max_refresh` budget, never a new per-round
allowance. Each retry uses a fresh screenshot and model answer. For example,
one unclear refresh plus one rejected-answer retry uses two of the default three
retries. Regeneration requires changed image sources/canvas or replacement
root/cell nodes; status text and selection classes alone are not sufficient proof.
An unchanged grid, unknown submission outcome or submit exception never causes
blind resubmission. A persistent preselection is not toggled. Retry exhaustion
requires human handling and records `attempts` (total model calls),
`verification_attempts` (verification rounds), and `retries`.
The default deadline includes verification, model and refresh budgets (capped at
3600 seconds); an explicitly configured timeout takes precedence.

Compose `flow.open` -> `action.click` (trigger sign-up/check-in) ->
`challenge.grid_captcha` -> `flow.result`. The challenge should stop on an
unconfirmed outcome so the output step cannot announce success prematurely. See
[the workflow example](execution.md#九宫格工作流组合) for a configuration without
site-specific credentials. Browser interaction and model-response enforcement
belong to the worker runtime; backend settings only validate and forward this contract.

Character-captcha recognition reads only the response message's `content`, never `reasoning_content`.
String content and arrays of `{type: "text", text: string}` are supported. Balanced
leading `<think>...</think>` blocks are removed; nested, incomplete, misplaced, or
reasoning-only wrappers are rejected. The remaining answer must be a single ASCII
alphanumeric token, then pass the step's charset/length constraints. Prose, Markdown,
and other ambiguous output fail the vision step rather than extracting a guessed
answer or falling back to another method. Responses marked `finish_reason: "length"`
or `"content_filter"` are rejected. Requests use the selected entry's `max_tokens` setting;
some reasoning providers can consume the budget without producing final content.
Parsing cannot recover an answer that was never emitted, and provider-specific
reasoning budgets/token parameters are not automatically negotiated.

### Worker Model Errors

Worker model failures in `sign.image_quiz`, `challenge.image_captcha` and
`sign.iframe.image_captcha` with `captcha_method=vision`, `challenge.grid_captcha`,
and opted-in `flow.result` judgement use `worker/vision.py`'s `ModelCallError`
(`ResultJudgmentError` for judgement). Its exception text contains only static
category/stage labels and an optional HTTP status, with no raw underlying exception
or cause chain. `model_error_data` provides structured step `data`;
`format_model_error` adds a Chinese troubleshooting summary to the step message
and `job.log` artifact. This is bounded diagnostic detail, not a full provider dump.

| Field | Meaning |
| --- | --- |
| `provider_error` | Static category: `http_error`, `timeout`, `network_error`, `invalid_json`, `invalid_response`, `no_tool_call`, `no_result`, `invalid_tool_call`, `schema_error`, `truncated`, `content_filtered`, `refused`, `invalid_input`, or `unexpected_error`. |
| `stage` | Model processing stage: `input`, `request`, `provider_response`, `tool_call`, `tool_arguments`, or `content`. This is not necessarily a precise network phase. |
| `http_status` | Optional status for `http_error`, not a response body or headers. |
| `timeout_phase`, `timeout_seconds` | Optional timeout phase (`connect`, `read`, `write`, `pool`, or coarse `request`) and configured model-request timeout in seconds, not measured elapsed time. |
| `provider_message`, `provider_type`, `provider_code` | Optional sanitized fields from a recognized JSON `{"error": {"message": "...", "type": "...", "code": "..."}}` envelope; `code` may also be an integer, converted to text. |

Provider detail extraction inspects at most 16 KiB of the error envelope. Oversized
or unrecognized bodies, non-JSON text and HTML are omitted, not copied into logs.
Only `error.message`, `error.type`, and `error.code` are considered. Known secrets
and endpoints, URLs and credential/header patterns are redacted; reflected
prompt/request dumps, images/base64 and markup are rejected. Control characters
are cleaned, each retained provider field is limited to 500 characters, and the
formatted summary to 2000. Raw transport exception text, URLs, API keys, headers,
prompts, images/base64 and reasoning are not diagnostic payloads.

These provider fields are **untrusted, admin-only diagnostic text**, never
instructions or authorization. Sanitization is not general DLP and cannot promise
to remove unknown private prose. Existing assistant single-step and curated
full-run projections remain limited to their static/typed diagnostics and Boolean
results; these richer fields and provider prose are not automatically fed to the
assistant. Explicit historical artifact reading remains a separate authorized,
sanitized evidence path, not an expansion of those projections.

Existing outcomes and `reason` values are unchanged: character-captcha model
failures return `fail` / `provider_failed`; quiz and grid model failures return
`waiting_human` / `vision_failed`; result judgement failures return `fail` /
`model_judgment_failed` without a Boolean result. Legacy/unclassified feature-boundary
exceptions are conservatively mapped to `invalid_response` (the grid retains its
recognized legacy HTTP/timeout/network categories), never their raw cause. New
client failures may use `unexpected_error`; neither label proves a more precise
cause. Unclear-answer refresh/retry rules and counters remain unchanged; HTTP,
network or response failures do not gain automatic retries or model/OCR fallbacks.

The outer step deadline is separate from `SITEFLOW_MODEL_TIMEOUT` (model request,
default 30 seconds). An outer timeout can end the step before model diagnostics
arrive and retains `stage=step_execution` / `reason=execution_timeout` (or existing
assistant outcome-uncertainty semantics). A generic failure after roughly 30
seconds cannot alone distinguish the two, HTTP failure or invalid output. Transport
errors also do not always identify a precise network phase; a coarse `request`
label must not be turned into a guessed connect/read diagnosis. These diagnostics
change no default step/request budgets, response-size budgets or `max_tokens`
behavior, and do not retroactively explain historical failures.

## Feature Policies

`GET /features` adds `defaults`, `required_fields`, `base_required_fields`,
`customized`, and `execution_settings`. Defaults include code default factories.
For image-captcha features, defaults include `captcha_method` (default `ddddocr`).
`execution_settings` is an object with `llm_prompt` for
`challenge.image_captcha`, `sign.iframe.image_captcha`, `sign.image_quiz`, and
`challenge.grid_captcha`.
`flow.result` uses the result-judgement contract below; other features return null.
`config_schema` reflects effective defaults and
required fields; types and constraints remain code-defined.

`PUT /features/{key}/settings` accepts:

```json
{
  "defaults": {"captcha_method": "nexusphp_gd5", "length": 6},
  "required_fields": [],
  "execution_settings": {
    "llm_prompt": "Read the captcha. Return only its characters."
  }
}
```

`defaults` and `required_fields` are required. `execution_settings` is optional;
omitted or null preserves existing behavior. A supplied object replaces behavior
settings, with omitted members taking code defaults. `llm_prompt` is a string of
1-4000 characters. Unknown execution-setting members are rejected. Non-null
execution settings for unsupported features return 422. Behavior fields in
`defaults` or `required_fields` return 422.

The endpoint returns the updated FeatureView. This replaces the stored customization;
unspecified defaults still inherit code defaults. Unknown fields and invalid defaults
are rejected (422). A code-required field can be relaxed only if the supplied policy
provides a valid default. Complete default sets also run model-level validation.
`DELETE /features/{key}/settings` resets to code defaults and returns FeatureView.
Unknown feature keys return 404. Policies use AppSetting JSON at `feature.<key>`;
`execution_settings` is stored separately from `defaults` and `required_fields`.

Workflow resolution merges policy defaults before template/site configuration and
runs the original full model validation. Existing explicit step values take priority;
policy edits do not rewrite saved steps or historical snapshots.

`captcha_method` selects the recognition method, defaulting to `ddddocr`.
Captcha, image-quiz, and grid prompts belong only in `execution_settings.llm_prompt`, not
in step config or policy defaults. Output-result steps additionally support the
optional per-step prompt described below. Unknown fields are rejected during validation.
DELETE resets both config customization and execution behavior to code defaults.

## Result Judgement

The `ResultExecutionSettings` contract controls model judgement for `flow.result`.
These controls live in Features management and provide the global gate, input mode,
scope, provider/model selection and common prompt. Each output step must also opt in.

| Field | Default | Meaning |
| --- | --- | --- |
| `llm_enabled` | `false` | Master switch. When off, all step-level model settings are ineffective. When on, only explicitly opted-in output steps can invoke the model. |
| `use_vision` | `true` | Send only the current page screenshot, not page text. Select an eligible `feature_cards` vision model. When false, send page text without a screenshot; text-only entries are eligible. |
| `judgment_scope` | `"success_only"` | Revalidate only output steps whose effective `output_value` is `true`. `"all"` judges both True and False output steps. |
| `model` | `""` | Optional upstream model-name override, at most 256 characters. Empty uses the selected registry entry's upstream model name. |
| `llm_prompt` | Chinese business criteria to check login and signed-in status and describe visible evidence | Business criteria, 1-4000 characters. The worker separately adds a fixed system tool-output protocol; users do not need to write output-format instructions. |

The model override is a free-text upstream string, not a registry ID or a provider
selector. First select the eligible `feature_cards` connection for the input mode;
the override changes only the outgoing model name on that selected provider's
endpoint/API Key, not priority, usages, capability or provider selection. All dependent
controls are disabled while the master switch is off; their values are retained.
Prompts and model IDs remain subject to validation even while disabled so the saved
settings satisfy the backend contract.

Example settings payload (omit `model` or use `""` for the selected entry's model):

```json
{
  "defaults": {"output_value": true, "message": ""},
  "required_fields": [],
  "execution_settings": {
    "llm_enabled": false,
    "use_vision": true,
    "judgment_scope": "success_only",
    "model": "",
    "llm_prompt": "检查页面是否明确已登录且今日已签到，证据不足则判为未完成，并简要说明可见依据，不包含账号或秘密。"
  }
}
```

The example prompt illustrates the default intent; the editor displays the default
prompt returned by the backend rather than maintaining a separate frontend copy.
The feature card always advertises LLM support for `flow.result`. A step's LLM badge
appears only when both global and step-level `llm_enabled` are on and its effective output matches the scope.
Effective output follows local configuration, inherited configuration, then feature
defaults (including global policy defaults); explicit False must not be treated as
missing. Text-only judgement still uses an LLM and receives the same badge.

Enabling judgement sends the screenshot or page text to the external provider;
this may include account details or other sensitive page content. Missing provider
configuration, unsupported vision, request errors, and invalid answers fail the
step. They must not silently fall back to the configured output value, a different
model, or the other input mode.

A valid False conclusion is a successfully evaluated step that outputs false and
fails the site task; a True conclusion outputs true. Model judgement replaces the
configured result within the selected scope. Failed model calls produce no Boolean
output and follow the step's error policy; choosing `continue` can therefore allow
later steps to run. The worker uses a system prompt to require a JSON object directly
in message content, without declaring tools, setting `tool_choice`, or forcing a
response format. It requires exactly `result` (strict boolean) and `reason`
(nonblank string, 1-500 characters). Nonempty tool calls are rejected as
`invalid_response` at `provider_response`; tool arguments are never read. Grid
recognition retains its separate tool protocol. Natural-language conclusions, Markdown,
duplicate JSON keys, extra fields and malformed JSON are rejected. Balanced leading
think blocks may be stripped from content; `reasoning_content` is never a result.
The default step deadline allows the provider timeout plus screenshot overhead;
an explicit step timeout still takes precedence. Requests are cancellable and are
never automatically retried. Page text is limited to 24,000 visible body characters;
vision uses the active page viewport screenshot, not the desktop or other tabs.

### Per-Step Opt-In

In site/template output-result cards, `config.llm_enabled` defaults to false.
Existing saved steps that lack this field remain off even when the global switch
is enabled; no migration or automatic opt-in occurs. The UI disables the local
controls while the global switch is off, retaining saved choices for later use.

`config.llm_prompt` is optional (at most 4000 characters). A nonblank value overrides
the common business criteria; an empty/whitespace-only value uses the global prompt.
The immutable output protocol is a separate system message, never merged into saved
user configuration, and takes precedence over user-specified output formats. Both fields follow normal
template inheritance: a site can override inherited true with false, or override
a template prompt with an empty string to use the global prompt. Reset controls
remove the local override and restore inheritance. Input mode, model selection
and judgment scope remain global.

The model returns JSON content such as:

```json
{"result": false, "reason": "The page still shows a pending check-in action."}
```

The reason is sanitized against known job secrets before normalization or truncation,
stored in step `data.judgment_reason`, and included in the execution log, not task
`outputs`. It is untrusted model text and may still reveal unknown page privacy;
sanitization is not comprehensive DLP. Existing configured result messages retain
their prior semantics and are not replaced by the reason.

Failures retain `reason=model_judgment_failed` and add a fixed `provider_error` code,
`stage`, optional `http_status`, timeout metadata and sanitized provider fields as
described in [Worker Model Errors](#worker-model-errors). Codes distinguish HTTP
errors, timeout, network errors, missing results, unexpected tool calls, invalid
JSON or schema, truncation, content filtering and refusal. Evidence collection
errors use `evidence_error`. Logs include
these bounded diagnostics and elapsed time, never raw provider bodies, arguments,
credentials or transport exception text. Calls remain non-retrying and cancellable.
