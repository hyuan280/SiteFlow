# 外部 Agent 与 MCP 授权设计

状态：调研与设计建议，**尚未实现**。本文不代表已经提供外部 Agent API、MCP Server、外部身份认证或独立审批中心。具体协议、接口和存储结构在后续实施时确定。

## 背景

当前智能助手的授权与会话关联：工具创建持久交互请求，SiteFlow 页面通过详情或 SSE 展示面板，用户确认后恢复同一次工具调用。单次交互最多等待 180 秒，等待用户的时间不消耗对话执行预算。

这适合内置助手，但不能直接作为所有外部调用方的授权协议：

- 其他 Agent 不一定有交互界面，也不一定支持长时间挂起工具调用。
- MCP 客户端的交互能力不一致，不能假设都支持 elicitation。
- 无人值守任务需要预先限定的权限策略，而不是每次要求用户打开页面。
- 当前目标、审批与成功运行证据部分绑定聊天会话，不能直接跨调用主体复用。

目标是保留现有安全边界，将授权从特定聊天页面中抽离，支持多种接入方式，而不是为外部 Agent 绕过确认。

## 三层边界

| 层次 | 责任 | 原则 |
| --- | --- | --- |
| 身份认证 | 确定调用者及其所属用户或组织 | 外部 Agent 使用独立身份；传输认证不等于操作授权 |
| 权限策略 | 决定该身份通常可以调用哪些能力 | 限定工具、站点、可改字段、车道、有效期及必要的调用限制 |
| 操作确认 | 决定这一次冻结的具体操作是否允许 | 高风险操作逐次审批，或由明确配置的窄范围策略放行 |

外部身份应与实际审计主体关联，不能让所有调用都伪装成同一个人或仅记录 `assistant`。保留业务执行身份的同时，另外记录实际调用主体、批准人、来源和关联操作。

## 三种授权模式

| 模式 | 适用场景 | 行为 |
| --- | --- | --- |
| 交互确认 | SiteFlow 页面、支持交互的客户端 | 展示宿主生成的操作范围，确认后继续 |
| 异步审批 | 无界面、连接超时短或不支持交互的客户端 | 返回审批编号和审核入口，稍后查询并恢复 |
| 策略预授权 | 定时运行、无人值守 Agent | 只有操作落在预先配置的范围内才放行，否则审批或拒绝 |

推荐以**独立审批服务及异步生命周期**为基础，交互弹窗只是其客户端之一。不要要求所有 MCP 客户端支持同一种弹窗或保持请求连接。

## 独立审批生命周期

建议的逻辑流程：

1. 验证调用主体，解析严格的工具参数，并检查业务前提。
2. 将目标身份、规范化参数、配置版本和风险范围冻结为操作提案。
3. 权限策略明确允许则签发受限执行能力；否则创建待审批记录或返回拒绝。
4. 审批人核对宿主生成的范围，批准或拒绝；超时、取消和失效均不产生权限。
5. 恢复时重新验证调用主体、目标身份、配置版本和业务前提，再执行批准的冻结操作。
6. 持久化执行结果，重复查询或恢复返回原状态，不重复派发副作用。

首次调用可以返回以下**示意结果，非已实现 API**：

```json
{
  "status": "approval_required",
  "approval_id": "opaque-approval-id",
  "review_url": "https://siteflow.example/approvals/opaque-approval-id",
  "expires_at": "2026-12-01T12:00:00Z"
}
```

审批编号只是查询关联标识，不能充当无需认证的批准链接或执行令牌。审核页面仍需身份认证及相应的浏览器请求防护；查询和恢复需要验证调用主体及授权关系。

批准后应执行服务端保存的冻结操作，**不能让 Agent 重新提交一份参数并默认继承原批准**。如需重新提交，必须与冻结参数指纹完全一致。

建议区分操作审批和执行状态：待审批、已批准、已拒绝、已过期、已取消、已失效，以及执行中、成功、失败、结果不确定。具体状态机在实施时定义，尤其需要处理批准后配置变化、服务重启、执行结果丢失和取消竞态。

## MCP 适配

- 支持 elicitation 的客户端可以用于收集选择或非敏感信息，并将答复交给 SiteFlow 审批服务验证。
- 不支持 elicitation 的客户端使用审批编号、SiteFlow 审核页面和查询／恢复机制。
- elicitation 的可用形式、客户端能力协商及协议版本应在实施时核对；不能假设协议传输的普通答复天然等同于有权审批人的确认。
- 模型文本中的“用户已同意”、调用参数中的 `confirmed: true` 或 `user_requested: true` 都不是授权凭证。
- 密码、Cookie、API Key、OTP/TOTP 等不通过普通询问工具或模型上下文收集。
- HTTP 接入和 MCP 接入应复用相同业务服务、权限判定和审批记录，不各自维护一套安全规则。

如果采用远程 HTTP MCP，应根据选定协议版本实施其适用的授权机制，校验令牌的资源及受众、权限范围和有效期。不要把现有浏览器 Cookie/CSRF 接口直接当成外部 Agent 的认证方案，也不要让模型获得可长期转发的管理员凭证。具体身份供应商和凭证方案尚未选型。

## 策略预授权

示例策略可以限定为：

> Agent A 只可操作站点 12 和 18；可读取脱敏配置和运行结果，可触发已保存工作流；只能修改 `checkin_after` 与 `timezone`；不得扩大可信 URL、切换凭据来源或启用自动调度。

策略至少应考虑：

- 调用主体和可代办的用户范围。
- 工具及动作类型，而非仅允许连接 MCP Server。
- 站点 ID 与不可复用的持久身份，防止删除重建后的 ID 混淆。
- 允许修改的字段、值域、运行车道及跨源权限。
- 有效期、撤销、并发和调用额度。
- 是否仍需逐次审批，以及哪些操作必须拒绝或升级审批。

不建议提供默认全开的“允许该 Agent 使用全部工具”。可信 URL 扩大、凭据来源变化、首次启用自动调度等操作默认保留逐次审批。

预授权不能绕过业务守卫。例如，启用调度依然需要当前站点及当前配置的成功完整运行证据；结果不确定的操作也不能通过换操作编号自动重试。

## 数据与执行约束

独立审批记录建议包含调用主体、代办用户、工具、目标持久身份、冻结参数及其指纹、审批范围、配置版本、创建／到期时间、批准人、处理结果和执行关联信息。敏感内容按现有加密和最小披露规则处理，公共响应不包含私有能力令牌或凭据。

执行能力应绑定调用主体、操作和目标，有明确期限、有限次数及撤销语义。服务端在执行前消费能力并记录幂等操作，不能把页面点击、审批结果或持久聊天摘要本身当成执行凭证。

关键不变量：

- 同一操作的重复请求、重复批准和连接恢复不重复执行。
- 参数、站点持久身份、关键配置或权限变化导致旧批准失效。
- 拒绝、过期、取消及服务重启不自动执行待审批操作。
- 执行后响应丢失标记为结果不确定，不能直接假设失败并重派发。
- 浏览观察可信来源不自动成为凭据可信 URL；单步、截图、配置写入和完整运行的权限保持可区分。
- 审批等待期限与网络请求超时、执行预算分别定义；异步模式不需要长期占用聊天任务、数据库会话或工具连接。

## 成功运行证据

现有助手启用调度的校验绑定同一用户、同一聊天会话、站点身份和当前配置。外部接入后，应评估将其改为**调用主体／授权用户、站点持久身份与被测试配置**的证据，会话仅保留为来源记录。

不能直接放宽为“任意 assistant 任务曾经成功”。仍需检查完整 Run 与目标 Job 均成功、提交不是不确定状态、没有取消、实际测试配置匹配，并明确模板和功能策略变化如何影响证据。

是否允许同一用户的不同 Agent 或不同会话复用证据、删除聊天后是否保留证据、哪些调度或备注字段变化不要求重测，都属于后续必须显式确定的策略。不得为此削弱现有执行前配置守卫。

## 分步实施建议

1. 抽取独立授权／审批服务和受限执行能力，先保持内置助手的现有行为。
2. 将当前页面改为审批服务客户端，补齐持久异步查询、撤销及恢复机制。
3. 引入外部调用主体及身份认证，先开放脱敏只读工具。
4. 增加 HTTP/MCP 适配，并测试支持与不支持 elicitation 的客户端。
5. 开放少量受控写工具和运行能力，加入逐次审批及严格幂等。
6. 最后增加管理员配置的窄范围预授权策略和跨会话成功证据政策。

验收重点包括：主体隔离、参数替换、越权目标、ID 删除重建、审批重放、过期／撤销、配置漂移、重复执行、取消竞态、重启恢复、未知执行结果、客户端能力降级及日志／模型中的秘密泄露。
